# π0.5 idea2：提交瓶颈、选择性重叠与固定条件准备

实验日期：2026-10-21。1/5/10 步正式矩阵、组合方案独立复测和原生 JAX 对照已完成。推荐显式启用 **Graph + Vision-only overlap + 等待上一轮完整 Prefill + 固定时间条件投影准备**，用于降低现有旧 KV 异步接口的动作响应延迟；既有默认配置不变。

独立复测的 CPU→CPU P50 分别为 **42.67 / 48.23 / 60.51 ms**，P95 为 **43.20 / 49.91 / 62.46 ms**。D10 相对原全重叠 Graph 的 91.32 ms，动作响应约 **1.51×**；相同准备配置下双分支完成时间仅从 97.08 降至 90.36 ms（约 **1.07×**）。D1 的双分支完成时间反而从 74.07 增至 80.42 ms，因此该配置不是所有指标上的最优。若调用方必须等待本轮新 KV 也完成，不能把动作提前返回的收益直接用于该接口。

## 范围和对照口径

本轮使用 `pi05_libero`，动作长度 H=10，分别测 D=1/5/10。此前 π0 的 H=50、D=10、82.46 ms 结果是另一配置，不能作为本轮直接加速比分母。原始 JAX checkpoint 经 OpenPI 自带转换工具生成 PyTorch checkpoint；811 个训练参数的映射和形状检查通过。权重、精度、动作数量、噪声、时间递推和采样规则在同一步数的对照间保持一致。

保留跨观测语义：AE 一次请求始终读取同一个完整旧 KV，后台 Prefill 构建下一份完整 KV。Pool 仍只有两个 Slot，Pool 修改只发生在调度 Host；Lease、epoch、generation、读者结束 Event 和完整 Prefill Event 决定槽位复用及发布。没有第三份完整 KV，没有逐层混合新旧版本，没有 Draft/Verify。

第二个建议中的“当前 VLM 层 KV-ready 后提前运行 AE”属于同帧逐层依赖，不能同时满足上述完整旧 KV 语义。本轮不引入这条依赖；旧 KV 在 AE acquire 前已经完整可用。细粒度实验使用 GPU Event 控制计算阶段的放行时机，不提前发布任何部分 KV。

另行量化了兼容旧 KV 的潜在窗口：上一轮 Prefill 最后一层 K/V 已生成，但最后层 Attention、输出投影、FFN 和最终 norm 尚未完成。GPU0 独占诊断在最后一次 `DynamicCache.update` 后记录 external CUDA Event，捕获全部原始 Prefill 计算；预热 10 次后交替 13 个输入测 100 次。KV-ready→Prefill-end 的 mean/P50/P95 为 **1.6088 / 1.6087 / 1.6138 ms**，完整 Prefill P50 为 40.8131 ms。13 个最终完整 KV digest 均与 eager 相等，地址固定、重捕获 0；Event 每次 replay 更新的语义单独验证。该约 3.94% 的隔离窗口不是请求收益或并发上界的严格证明，竞争后时长可能改变。它只说明存在一个较小的尾部机会。结合 FFN 配对的竞争结果，本轮不改 Pool 的完整发布契约：所有读取仍等待 full-end，不提前覆盖尾部还在读取的槽。源码、原始 CSV、校验和复现命令保存在 `results/idea2/cewp_20261021/kv_ready_tail/`。

测试采用同一任务的 13 个不同观测交替输入，固定观测/state 输入序列和 CUDA noise seed；各对照匹配同一记录，13 条记录之间的观测和 state 会变化。每个候选预热 10 次；正式比较至少 100 对 AB/BA，另做 100 次连续请求并覆盖 reset。配对比较固定相同旧 KV 来源与当前观测；连续实验记录实际消费来源，不能用每对重置的结果代替连续时效性。编译、捕获、预热不计入稳态。

数值门在实验前固定为 normalized/decoded action 的 max error ≤1e-5、MAE ≤1e-6。参考是原始 eager 在**相同旧 KV**下的输出。不同 D 分开比较；原生 JAX fresh-KV baseline 只用于跨框架性能参考，不作为旧 KV 数值 oracle。没有进行闭环任务成功率实验。

OpenPI 子仓库已有其他实验遗留文件，本轮没有还原或修改它们。原生 baseline 的专项审查确认：`pi0.py` 仅注释变化、AST 与 git HEAD 一致；SigLIP 的视觉压缩默认为 `off/256`，同权重关闭路径的输出与 JAXPR 与原文件相同。原生测试启动时强制检查压缩关闭，并保存实际 import 源文件哈希、git HEAD/status；非关闭配置直接失败，不静默修改模型。证据为 `native_source_audit.json` 和各原生结果的 `native_provenance.json`。

性能采集与 nsys 分开。正式计时使用 GPU2；请求 profile 使用 GPU1，两者同为 RTX 4090，但不能混用它们的耗时作为加速比分子/分母。CPU→CPU 包括实际预处理、GPU 提交、等待、输出拷贝和后处理，不包含 RPC 网络传输。AE 内部动作可用时间和实际 API 返回时间分别记录；serial 模式可能已经算完动作，但仍在请求返回前完成 Prefill。CUDA Event 时长包括等待和执行空隙，不等于 kernel busy time。真实重叠由 nsys kernel 时间区间交集计算，不使用 NVTX 区间交集代替。

## 已确认的原因

1. **eager 单 Host 提交是首要瓶颈。** π0.5 D10 GPU2 的连续实验中，AE CPU 提交 P50 263.99 ms，Prefill 66.72 ms。两个 Stream 不会自动让尚未提交的 kernel 并行。D10 的 eager AE 在 100/100 次提交函数返回时完成 Event 已就绪；Graph 模式为 0/100（`submission_completion_states.json`）。原始 `build_prefix()` / `generate()` 的正常路径没有全设备 synchronize、`.item()`、`.cpu()` 或 `nonzero`；必要的结果 D2H、AE 完成等待和生命周期等待没有删除。输入准备的 H2D 发生在分支提交前，单独归入端到端时间。
2. **Graph 后确实重叠，但资源竞争抵消大部分收益。** D10 full Graph 的 AE 优先高优先级 trace，真实 kernel overlap/union=59.11%；eager Prefill-first 仅 0.80%。Graph serial 的 kernel union 为 72.67 ms，并发为 62.33 ms：36.84 ms 的交集被 26.50 ms 的分支 busy time 膨胀抵消。相同 kernel 和几何形状的 AE WMMA 平均约 1.64 倍、FP32 GEMV 约 1.20 倍；VLM 主 GEMM 约 1.11 倍。这里是时间线证据，未采集 SM/DRAM 硬件利用率，不能把具体瓶颈归因于某个资源计数器。
3. **选择性重叠必须同时约束 KV 时效性。** 只让 Vision 和 AE 重叠会提早返回动作，但剩余 VLM 可能跨越下一请求，100 次连续运行曾出现平均 KV 年龄 2.09。这个配置虽然 P50 约 64.61 ms，却不能作为成功结果。增加可选的 `await_previous_prefix`，在下一次 acquire 前等待上一观测的完整 Prefill Event，再 poll/publish，恢复年龄 1；不等待本轮新 KV、不改变 AE 的旧快照。
4. **固定时间条件存在可移出的重复工作。** π0.5 每步 37 个 adaptive RMSNorm dense(condition)，D10 共 370 次，读到相同的当前步时间条件。原始 trace 中相应 FP32 GEMV 约占 AE busy time 17.8%。按原来的 CUDA FP32 时间递推、sinusoidal、MLP 和 Linear 舍入路径预先准备每槽只读条件，可避免每次请求重新计算。它不是图像 hidden states/KV 缓存，也不改变 Euler 更新。

选择性 Graph 每槽有 Vision、VLM、AE 三个不同私有内存池。AE 读取被 Lease 固定的旧槽；Prefill 只写另一个已独占预留槽。`vision_only` 要求 AE-first，VLM Stream 等待 AE 完成 Event；`vlm_only` 要求 Prefill-first，AE Stream 等待 Vision 完成 Event。这些阶段等待全部入 GPU 队列，没有逐层 CPU synchronize。

同请求阶段约束不自动约束下一请求：D1 未加 `await_previous_prefix` 时，虽然同请求 AE×VLM 交集为 0，下一请求 AE 仍与上一请求 VLM 重叠，5 个 profile 请求累计约 6.094 ms。加等待后跨请求 AE×VLM 交集也为 0，并恢复 5 次完整 Prefill。因此 `await_previous_prefix` 同时约束快照时效性与跨请求的阶段竞争。连续流水线的重叠报告使用全测量窗口的 kernel 交集，另保留同请求统计；例如 D1 full Graph 全窗口为 12.62%，同请求仅 6.98%。

Modulation 的 Python forward 临时替换只发生在单 Host 的冷预热/捕获期，在 `finally` 恢复；稳态 replay 不执行 Python 替换。每槽缓存约 4.55 MB（D10）的条件投影，未新增完整 KV。权重必须在 Graph 生命周期内保持不变，与现有静态 Graph 的约束一致。

最终审查还修复了已存在的输出异常清理缺口：CPU output transform 抛异常后会遗留旧 Lease，使 reset 失败。现在该异常路径先排空所属 AE/Prefill Stream，再释放 Lease、reset Pool 和阶段 Event 标记；正常路径不增加同步。真实 Pool 的 CPU 回归覆盖两种提交顺序、Host Worker、尚未完成的 Prefill、可恢复的 Event 等待异常以及失败后再次预测。相关完整 CPU suite 为 41 项通过。

## 负结果与选择依据

compile-only 与 compile+Graph 均关闭自动 cudagraph 后测试。D1/D5/D10 的 normalized action 最大绝对误差分别约 0.02365 / 0.006099 / 0.006067，均超过预定门，因此停止这些候选的正式性能评比。失败数据保留在 `compile_failures.csv` 和各 `compile_*` 目录；不能拿不等价计算宣称收益。

阶段微基准表明存在并行空间，但只在部分组合成立。重复 100 AB/BA 的 VLM QKV×AE Attention 约 1.24–1.25 倍、QKV×AE FFN 约 1.17–1.19 倍；VLM FFN 与 AE 阶段配对仅约 1.01–1.02 倍，AE Event 跨度还可能显著变长。这里的加速比来自共同 release 之后到两个分支均完成的 CUDA Event 时长，不是 kernel busy time 比。为测量很短的阶段，微基准使用共同 GPU release gate；该 gate 排除在 Event 计时起点外，nsys busy 统计也剔除对应 release kernel；诊断 gate 没有进入生产路径。微基准不作为请求加速证据，实际集成只选择了更小的 Vision/VLM 边界。

未继续做自定义 attention 或 QKV 打包：原始 AE 的 cat 总计约 1.56 ms/请求（4.91%，且包含 RoPE/mask，不能全归为 KV 拷贝），QKV signature 总计约 8.58%，都不是完整可消除开销。现有每层将旧 prefix 与当前 suffix 拼接，但没有每步 clone 整份旧快照；不为省拷贝引入可写共享 KV。实际 π0.5 GQA Q/K/V 输出宽度为 2048/256/256，不能照搬三等分。先用精确的固定条件准备获得收益，避免在证据不足时扩大重构。

GPU3 的独立准备项消融使用同一双槽、同一调度：每项 100 对交替顺序测量，另做每配置 100 次连续运行。Schedule-only 相对 baseline 的配对加速比中位数在 D1/D5/D10 分别为 0.993× / 1.003× / 1.011×，收益不稳定；进一步准备 norm modulation 相对 schedule-only 为 1.019× / 1.064× / 1.099×。这说明主要收益来自重复的条件投影。不能把这两组独立 ratio 的中位数相乘，冒充直接配对的净收益。三种步数共 2100 个动作输出全部误差为 0，组合配置保持年龄 1 和发布/消费频率。

## 原生 π0.5 JAX baseline

同 GPU2、观测序列和显式噪声，每个 D 预热 10 次后测 100 次。JAX 与 PyTorch fresh-serial 都使用本帧新 KV；异步候选使用上一帧完整 KV，语义不同。这里只比较延迟，不声称跨框架逐位相等或闭环成功率等价。原生基线将显式 CUDA noise 生成移到计时外，包含 noise H2D；PyTorch 计时仍含 noise 生成。

| D | JAX CPU mean/P50/P95 ms | PyTorch Graph fresh P50 ms | 合格旧 KV 候选 P50 ms | JAX P50 / 候选 P50 |

数值门、样本数、Graph 重捕获、各模块提交/等待、完整优化组合与负结果详见 comparison.csv、paired_comparison.csv 和 summary.json。

PyTorch 表中显存为预热后重置统计的 allocator allocated/reserved 峰值；长矩阵进程可能保留先前配置的 allocator reserve，因此独立新进程复测更适合看最终候选的占用，约 7.09–7.10 / 7.65–7.66 GiB。JAX 的设备显存采样峰值 D1/D5/D10 为 8622 / 8622 / 8638 MiB（500 ms 采样，包含 context/driver，可能漏掉瞬时峰值）；另保存 allocator lifetime peak，包含加载/预热，不能与 PyTorch 稳态 allocated 直接相减。

## 复现命令

从仓库根目录执行，使用独占的 GPU；所有输出目录必须不存在，以免覆盖已有证据。正式数据使用 GPU2（UUID `GPU-83fdf473-8633-29d3-4a42-e482cfdf0c25`）；GPU3 的准备消融与重复验证单独列出，不混入同卡加速比分母。

```bash
export CUDA_VISIBLE_DEVICES=2
export JAX_PLATFORMS=cpu JAX_PLATFORM_NAME=cpu
export OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4
export OPENPI_DATA_HOME=/root/nfs/embodied/benchmark/shared/checkpoints/openpi
export PYTHONPATH=.:policies/openpi/src

# 匹配旧 KV 的串行/组合候选：100 对 AB/BA + 各 100 次连续请求。
# 分别将 --steps 改为 1、5、10，输出目录也相应改变。
policies/openpi/.venv/bin/python -m preparations.idea2.cewp_bench \
  --checkpoint shared/checkpoints/openpi/pi05_libero_pytorch_idea2 \
  --output results/idea2/repro_d10_combo --steps 10 \
  --warmup 10 --count 100 --continuous-count 100 \
  --pairs graph_serial_high:graph_ae_high \
  --continuous graph_serial_high graph_ae_high \
  --selective vision_only --await-previous-prefix --hoist-modulation

# 准备项的真正单变量比较：baseline→schedule→modulation，同一双槽与私有 Graph。
policies/openpi/.venv/bin/python -m preparations.idea2.cewp_preparation_pair \
  --output results/idea2/repro_d10_preparation --steps 10 \
  --selective vision_only --await-previous-prefix \
  --warmup 10 --count 100 --continuous-count 100

# 原生 JAX fresh-KV 对照；工具会在首次 import JAX 前切到 CUDA。
policies/openpi/.venv/bin/python -m preparations.idea2.cewp_native_baseline \
  --output results/idea2/repro_native_d10 --steps 10 --warmup 10 --count 100
```

原始 eager 串行/双流分别选择 `eager_serial`、`eager_dual_ae_first`、`eager_dual_prefill_first`，去掉三个优化开关。Graph 基线选择 `graph_serial`、`graph_ae_first`、`graph_prefill_first`；高优先级版本为 `graph_serial_high`、`graph_ae_high`、`graph_pre_high`。单独 AE/Prefill 用 `--kind isolated --pairs --continuous eager_serial graph_serial`。`--selective all` 测拆分开销，`--selective vlm_only` 必须配 `graph_pre_high`。每一配对的 Graph 与优先级配置保持一致。

完整原始矩阵和每项独立消融的确切 argv 存在 `matrix_status.json`、`followup_matrix_status.json`；重复实验存在 `final_repeat_status.json`。每个结果目录包含任务入口时磁盘源码快照和 hash。首批长运行矩阵早于最终 `policy.py` 的诊断字段与异常清理修复，已加载的 Python 模块不会随磁盘修改而更新；这两处修改不改变正常计算或同步路径，不能把中途磁盘快照声称为该进程所有模块的加载版本。最终关键重复实验用全新进程执行，并检查生产文件 hash 与最终源码一致。CPU oracle 只缓存参考动作，不缓存完整 KV。

单独采集 nsys，不能使用这次运行的延迟报告收益：

```bash
nsys profile --trace=cuda,nvtx --cuda-graph-trace=node \
  --sample=none --cpuctxsw=none --capture-range=cudaProfilerApi \
  --capture-range-end=repeat:2 --force-overwrite=false \
  -o nsys/idea2_experiment/repro_cewp_d10 \
  policies/openpi/.venv/bin/python -m preparations.idea2.cewp_bench \
  --checkpoint shared/checkpoints/openpi/pi05_libero_pytorch_idea2 \
  --output results/idea2/repro_profile_d10 --steps 10 \
  --pairs --warmup 5 --continuous-count 5 --reset-every 0 --profile \
  --continuous graph_serial_high graph_ae_high \
  --selective vision_only --await-previous-prefix --hoist-modulation

nsys export --type sqlite \
  --output nsys/idea2_experiment/repro_cewp_d10.2.sqlite \
  nsys/idea2_experiment/repro_cewp_d10.2.nsys-rep
policies/openpi/.venv/bin/python -m preparations.idea2.cewp_trace \
  nsys/idea2_experiment/repro_cewp_d10.2.sqlite \
  --output results/idea2/repro_profile_d10/trace_graph_ae_high.json
```

`cewp_trace` 提供按请求归属的统计。跨请求全窗口与阶段交集的审计命令、所有原始 trace 对应关系见 `request_profile_manifest.json`、`audit_request_traces.py` 和 `request_trace_summary.json`；必须核对 kernel launch 关联完整性和两分支工作量，尤其不能把少做 Prefill 的 profile 当公平对照。
