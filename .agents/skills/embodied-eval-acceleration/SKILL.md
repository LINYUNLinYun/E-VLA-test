# 具身实验与评测加速

目标是缩短从研究问题到可解释结果的时间。GPU 利用率是诊断信号，完成有效评测的速度才是选型指标。先复用已验证的方法，再用小批真实场景验证是否适用于当前模型、环境和机器。

这是项目内 skill。项目根目录为本目录的 `../../..`；定位后再读项目文件，勿假定工具默认工作目录。历史证据与实现入口见 [references/evidence.md](references/evidence.md)，只读与当前瓶颈相关部分。

## 1. 先确定最小实验量和可复用数据

- 从用户当前方案提取模型、checkpoint、mask、D／采样日程、预测 H、执行 R、suite/task/init、seed、settling、prompt、终止上限和输出需求。继承已授权范围，不另设审批流程。
- 快速验证优先小样本覆盖任务类型。没有另定规模时，可建议四套件各 10 task × 1 init（40 条／条件），有希望的配置补至每 task 5 init（200 条／条件）；已有指定矩阵优先，不擅自缩减。报告这是探索评测，不是官方 50 init 全量基准。首批计入扩样总数。
- 查现有 baseline 和候选数据，协议与 case 身份兼容就复用；不兼容则作历史参照，明确差异。不能只看模型名／总体成功率判定可合并。用户允许优先新实验时，不为了完美历史对照反复补跑。
- 先定本轮所需输出。通常保留配置、逐案例成功／失败、执行步数、时延、原始末端 XYZ、动作与必要阶段数据；全量视频、逐帧 RGB、全层激活只在研究需要时保存。若要求视频，预选代表案例，不用结束后的成功与否偷偷换样本。
- 完成一次针对性核验后复用其记录。固定 checkpoint／manifest 的 hash 可缓存；不要每个 episode 在全局锁内重新 hash 所有历史文件，也不要为增加验收覆盖反复解码全部视频。

## 2. 用小批 profiling 找瓶颈

默认先做约 10–20 分钟的有界探测；遇到长编译说明成本与收益，再决定是否值得继续。没有新线索不扩成优化工程。建议先用四套件各 2 个固定真实案例；失败或长轨迹占比较高时也要覆盖，不能只测很快成功的任务。

同时测两种工作负载：

1. **固定观测重放**：复用真实轨迹中的约 100–200 个请求及显式噪声，测模型和服务成本；先对实际 shape／prompt／route 预热，预热与测量分开。可从 20 次预热开始，仍有编译就单列冷请求，不把固定次数当热态保证。
2. **闭环小批评测**：同一批 suite/task/init，比较完整完成墙钟、有效 episode/小时、动作/秒、请求/秒、成功数及步数分布。不能拿固定 bank 的快直接证明正式评测快。

分解：服务加载／编译、环境创建／reset／settling、物理 step、必要相机渲染与扰动、RPC 排队／传输／推理、落盘。RPC 内再按需要区分 encode、VLM、action expert 和解码。只保存少量代表请求的 profiler trace，避免每层同步本身拖慢正式运行。

GPU 异步调用需在计时边界正确等待或使用 GPU events；单请求对照可同步，测跨 stream 重叠时不能在每模块后强制全设备同步。并行区间会重叠，不能把各 worker／模块时长简单相加当墙钟分解。CPU 采样短窗检查锁等待、渲染和 I/O，避免凭低 GPU 利用率猜模型慢。

## 3. 按优先顺序尝试工程优化

| 优先级 | 方法 | 适用与核验重点 |
| --- | --- | --- |
| 1 | 持续模型服务，精简非必要 I/O | 避免每回合加载权重／启动模型；保留策略需要的相机，取消额外视频和冗余 dump。压缩与不压缩的收益需实测。 |
| 2 | 同 task 连续 init，复用环境 | 重置完整官方状态、随机数、相机／扰动状态、任务成功状态与 policy episode cache；核初始观测和固定控制动作。每 task 只有一个 init 时可能无复用收益。 |
| 3 | 同卡 2 个独立环境 worker，共享一个 B1 服务 | 交叠仿真／CPU／I/O 和推理；B1 请求可串行。按 episode 隔离动作队列、KV／预测器状态和随机流，不能串场。先测 1→2，再按 CPU／渲染／队列瓶颈考虑更多。 |
| 4 | 多 GPU 分片 | 独立模型／条件／task 分片，各卡持续服务和独立端口；实际记录 GPU UUID 与执行 revision。可并行的待办分给其他已授权空闲卡，不无故等原来那一张。 |
| 5 | 缓存、batch、compile、CUDA Graph、双 stream | 由 profiling 指向再做最小对照；记录准备成本、shape 切换、内存与闭环收益。历史没有证明这些在所有模型／评测上都有效。 |

模型请求改变 D、H、R、mask、精度、采样器、跨帧 KV 或残差复用属于科学条件或近似推理，单独命名评测成功率；不要作为“保持算法不变的评测提速”静默上线。

同观测比较多个 AE 日程时，**同模型、同 mask、同视觉／语言输入**的确定性 VLM 前缀可考虑复用，各候选复制可变状态并绑定噪声身份。不同 mask、不同观测不能套用同一前缀。各变体自由闭环后 obs 会分叉，不能继续拿 baseline 的 KV 冒充各自实时观测；沿 Full 轨迹做 shadow 对比须单列实验口径。

## 4. 保留必要一致性，避免把验收做成主实验

- 优化前固定采用标准，遵守当前用户对逐位一致或容差的要求；失败后不能为了上线调大容差。保留同 input／noise／state／prompt 的原始与 decoded 动作比较，覆盖实际执行前缀、平移／旋转／夹爪和尾部最大差。
- batch 即使平均误差小，也可能让首几步夹爪翻转。检查每样本噪声、输入顺序与还原顺序。若当前允许近似分支，单独评测其质量；若要求 exact，就退回 B1，不因此放弃双环境 worker。
- 服务重启／跨 GPU 后有偏差，先固定预热调用史、route 顺序、shape、随机状态与 backend，再归因硬件。必要时做最小同服务对照，不无限重跑全矩阵。
- 工程改动只核受影响的输入、状态隔离和执行路径，再跑小批闭环；不层层添加与改动无关的审计。历史验证有效范围要写清，小批一致不声称全域数学等价。
- 新机器／环境迁移后重新小批测吞吐。v3.1 的双 worker 成功，不能直接证明 Plus runner 已获得同样收益。

## 5. 调度、上线和停止规则

- 在当前已授权设备集合内调度，尊重其他会话保留卡。不要把某次历史 GPU 编号写成永久资源规则；启动前确认当前归属。空闲率低不等于卡无人使用。
- 本项目现有偏好：**还有待调度工作且缺空闲卡时，约每 30 秒检查可用候选卡**；已有足够运行资源，或候选卡均由本轮任务占用时，不重复全卡扫描，依据自身 worker 完成事件补队列。明确排除的卡不扫描。一个调度者负责发现空闲卡，避免多个进程各自扫描。
- 任务键、seed／噪声不能由完成顺序决定。维护轻量唯一任务状态、原子领取和完成记录；卡被回收时仅重新分配未完成键，已有效失败也是有效结果。技术中断单列，有界恢复，不能把困难失败反复重试到成功。
- 保持持锁段短；重 hash、视频解码、报告生成放在锁外，能复用就不再执行。减少 NFS 小文件与重复整账本读写，精简保存不删除研究所需数据。
- 候选先通过同输入核验与闭环短对照。优先同服务交替 A/B 顺序，显著收益再上线；细小收益可补一次反向顺序，不能为统计“显著”无上限加测。准备／编译成本也计入预计总工期，剩余任务节省不足以回本就不切换。
- 在 episode 或预定 condition 完成边界切换，保留执行 revision，不热改在途策略。上线后用轻量增量计数复查，可参考 30／60 分钟窗口；持续无收益就在安全边界恢复已知配置，不为优化继续拖延主实验。小任务结束早则无需等足窗口。

## 6. 输出可执行的加速决策

交接给执行代理时，给出：实验规模／复用来源、当前可用卡与保留卡、每卡服务和 worker 数、分片／续跑规则、I/O 配置、profiling 结果、数值标准、采用配置、停止／回滚条件和输出目录。不要直接执行历史脚本里固定的端口、GPU 或旧队列。

结果表至少包含：配置、样本量、准备成本、闭环墙钟、episode/小时、动作/秒、成功数、数值核验结果。仅在需要时另列 encode／VLM／AE 的热态时延、请求时延和实际 batch 大小。

ETA 按各剩余分片的任务组成与近期有效吞吐估算，并行取最慢分片结束时间，再计必要收尾；不要把各卡总速率直接用于不可迁移的尾部任务。首次加载／编译、失败跑满上限的占比都影响 ETA，给区间并随实际进度更新。

把“模块快了多少”“同输入请求快了多少”“全部评测早完成多少”分开说。更弱的模型可能失败更多、回合更长，即使每请求更快也让实验总耗时变长。
